# tether — design v1 (draft)

> Working name. A Hermes plugin that gives one remote Hermes agent the **local capabilities of any
> paired machine**: its terminal and files, its real screen, its own MCP servers and skill tools, and
> what is installed where. Hermes connecting to Hermes. Hackathon entry, due 2026-11-11.

## 1. Decisions this design follows (the author, 2026-11-05/06)

| # | Decision |
|---|---|
| D1 | "Control my PC": one remote agent, full desktop capabilities on any paired machine; one agent, many devices. |
| D2 | **Host** = the agent's own Hermes (its sessions, memory, skills live only there). **Devices** = paired machines that lend their tools. Works through both the CLI and Desktop. |
| D3 | Hermes-to-Hermes: each device runs Hermes itself. What the remote agent may do on a device is decided by **that device's own Hermes settings** (Desktop or CLI). No second permission system. |
| D4 | **No new permission path.** Remote actions enter the device's Hermes through the same tool and approval path as local ones; OS permissions (macOS Accessibility / Screen Recording) are granted once, as for local use. The plugin's only new surface is the connection. |
| D5 | Pairing via a **master link that generates the code**; every boot an **automatic encrypted handshake**; **256-bit** encryption; no token you paste around. |
| D6 | Scope = **remote AI with local capabilities**: terminal/files, screen, opening pages and viewers, knowing what is installed and where, each skill's local tools. |
| D7 | Nothing extra for users to install beyond the plugin itself. |
| D8 | Approval UX (always-grants, phone approvals, bounded manifests) is tuned after it works end to end. |
| D9 | The CuaDriver shadow bug (hermes-agent #142314) is documented, not auto-fixed. |
| D11 | **Encryption suite is chosen automatically and non-invasively**: the user gets the best 256-bit connection for their device ↔ host pair; nothing on their system is changed. |
| D12 | **Desktop machines only.** Not for headless control: SSH already covers headless boxes, and they need no viewing or opening things. The plugin has no effect on headless or SSH setups. |
| D13 | **Keys and secrets follow Hermes's normal secure path** (the system's secure store, as Hermes already does). The plugin never asks for keychain access itself, and **the agent can never read the keys the link uses** ("Hermes should never have access to the very thing it uses"); this blocks prompt-injection exfiltration. *Corrected 2026-11-21 (D40): a program running as the machine's user, the agent's terminal included, can read the key file and its passphrase; tether keeps them from accidental exposure.* |
| D14 | **No control-arbitration layer.** Screen control is Hermes's built-in computer use, used as is (background-first input, no forced takeover); the plugin adds and changes nothing in that skill. |
| D15 | **A grant survives a reconnect** (link drop/return within the session and idle window keeps it). |
| D16 | **Long-running/background commands**: whatever is needed, as long as it conforms to Nous's plugin rules (public plugin API only, no core changes). |
| D17 | **Protocol versioning** (Claude's call): `hello` carries a protocol version; same major version required, otherwise a clear refusal naming both versions and the fix. |
| D18 | **Exposure follows Nous's rules**: authenticated non-loopback binds only; LAN/VPN/tailnet recommended per Hermes docs; nothing internet-facing by default. Docs cover the device's Hermes needing to run, plus an "offline: Hermes not running" status. |
| D19 | **Logging = Hermes's normal method** (its agent/tool logs and session records); no separate audit store, since agents can make thousands of calls. |
| D20 | **No host→device SSH, and either Desktop route.** The plugin must work without the host having SSH to the device (that defeats the purpose; tonight's SSH terminal backend and driver wrapper are stand-ins to remove), and with Desktop attached to the host by **either** route Hermes offers: *Remote gateway* (URL + login) or *SSH gateway*. The link is independent of that route; both are in the test matrix, plus the check that the device's own local Hermes keeps running in each mode. **Verified 2026-11-08:** Remote gateway (host in Docker) and SSH gateway (host on a Linux workstation, connected as the install's own user) both tethered the Mac with no host→device SSH. |
| D21 | **The device's rules apply on the device** (2026-11-06). Found live: Hermes's file tools judge paths with the HOST's rules (its homes, its `HERMES_WRITE_SAFE_ROOT`), so the NAS fence blocked every Mac path and the Mac's `~/.ssh` was not in the host's credential list. While a device is the session's target, the file tools' two path checks run on the device with its own Hermes rules (`path_check`, `pathpolicy.py`); unreachable = fail closed. `devices use` and the tool description tell the model the device's rules apply and a refusal is final (no routing around it via the terminal); the device announces whose rules apply. |
| D22 | **Device mode** (2026-11-06). While a device is a session's target the session works ON it, through public plugin surfaces only (catalog rule 9): `tool_execution` middleware hands the file tools (read_file, write_file, patch, search_files) whole to the device, where `model_tools.handle_function_call` runs them in the device's own Hermes (its hooks and middleware, paths, file rules, write fence, credential protections; relative paths resolve against the session's device cwd; D59); terminal and computer use keep their paths (tether backend, tether_screen), with the session's approvals. A `pre_llm_call` hook tells the model once per turn which machine it works on and that its rules apply, so no per-tool coaching. Replaces D21's path shim (which rebound two core functions). Every surface registers in every role and is inert until a role is set (declared == registered). Next: device-side approval relay so terminal/computer use can be handed over whole too. |
| D23 | **Only the user's words open or close a device connection** (2026-11-06). `pre_llm_call` records the user's own message: `devices use <name>` is accepted only in a turn whose user message names the device, and close only when it asks to close/disconnect/go home; the model's own calls, tool results and page text cannot switch machines. A new session starts at home; the device's `grant_idle_minutes` (announced) closes it after idle. Device work routes only inside a user turn (`pre_llm_call` → `post_llm_call`); Hermes's background review (thread `bg-review`, prompts "Review the conversation above…") never opens a turn, so its edits stay on the host. A scheduled job or sub-agent (platform `cron`/`subagent`) opens no turn and its words count as none; a tool call reaches the device only when its turn id is the user's open turn (a stopped turn never closes, so a later run would otherwise inherit it). File-tool paths inside the host's own Hermes home (skills, memories) always stay on the host, except a device's workspace and `~` paths that do not walk into the home (D60). Closing clears the attachment fallback (no pulling from the device after close). A call with no turn id (some of Hermes's helper threads) is judged by the open-turn rule alone, as before. |
| D24 | **Per-session workspace on the device** (2026-11-06). `<device data>/tether/sessions/<session>/` (0700) is where the session's terminal starts; the rest of the machine is reached from there under the device's own rules. `skill_view` while on a device copies that skill's folder read-only into `<workspace>/skills/<name>/` (tar, `filter="data"`, 20 MB cap, via the public `transform_tool_result` hook) and tells the model the path; skills are still changed only with `skill_manage` on the host. On close (user, timer), the device revokes the session's grant and removes the workspace (`close_session`, never asks for consent); a sweeper removes workspaces of lapsed grants within a minute; a device start wipes leftovers. How cleanup stays inside the workspace: D39, D55. |
| D25 | **Hermes's own gates run, one per kind of action; the device adds its own rules** (2026-11-07). Nothing in Hermes's approval path is skipped (the tether backend is not a container): in the host session a terminal command meets Hermes's dangerous-command gate (its card, session/always answers, smart mode, yolo), `execute_code` meets the execute_code gate, computer use its per-action cards, file tools Hermes's own checks on the host and then the device's own Hermes (D22, D59). While a device is the target the command runs only there; when Hermes's command gate checked it (noted by the provider's `skip_container_guards` read, which always returns false), the device adds its floors (hardline, runtime self-delete, `sudo -S` guess, its `approvals.deny`), so nobody is asked twice. A command that reached the device without passing that gate (an `execute_code` script's commands, internal calls) is judged by the device's full Hermes rules (`device_rules.judge`), and a flagged one goes back through Hermes's public `check_dangerous_command` in the host session before it runs. If the gate checked a command for a device and the connection closed before it ran, it runs nowhere. Missing Hermes helpers on the device = every flagged command asks. Host-owned work (memory, skills, its own Hermes home) stays on the host. |
| D26 | **Exact phrase to open** (refines D23, 2026-11-07). A connection opens only when a line of the user's own message starts with `tether <device>` (spaces, hyphens and case free; "please tether mac" does not open). Only the exact Hermes shapes are peeled off the user's text (the sender tag Hermes built for the turn, its labels, a voice note's transcript); a quote, a note, a link preview or a run no person typed (webhook, kanban, gateway, cron, sub-agent, or a process started from an agent's shell) counts as none of the user's words. Naming a device in ordinary talk is refused with a pointer to the phrase, so neither casual talk nor injected text can open a machine. Closing stays broad (`untether`, "close the connection", "go home"): dropping back to the host is the safe direction. |
| D27 | **A denial closes the connection.** When the person at the device denies a session, the host closes the session's connection (back to the host, workspace wiped) and tells the model nothing ran and only the user can reopen it, instead of staying pointed at the device and re-prompting on the next call. |
| D28 | **Tether panel** (Desktop, right sidebar; palette "Open Hermes Tether"; `mod+shift+e`). Host view: paired devices, status, the opening phrase, idle limits, rename. Device view: the settings that machine owns (idle limit, consent wait, pause), applied live through a settings file the device polls. Both: a connection log (`events.jsonl`: kinds, times, labels, a 6-character session id; never commands, paths, keys or addresses). The panel's backend reads live status through the gateway's link relay and never takes the link itself. |
| D29 | **Labels and two idle limits.** The host can rename a paired device; its label is the word that opens it. The host may also set its own idle limit per device; the shorter of the host's and the device's limit applies, so the device's own setting stays the ceiling. Both count time the machine was asleep, and a call still running is never idle (no idle check closes a session with a call in flight). |
| D30 | **A computer's own name never leaves it.** Devices do not announce their hostname, and the host strips one from older devices, so it never reaches the panel, the `devices` tool or a chat. |
| D31 | **`untether` is a solo command** (replaces the broad close of D23/D26; found in use, 2026-11-10: in a live chat, `untether` only worked dependably as a message on its own, so the plugin now accepts it only that way and says so). A connection closes on the user's words only when their whole message is `untether` (case and a trailing `.`/`!` free). "untether mac", "ok untether", "close the connection" or "go home" do not close it; the agent keeps working and tells the user to send `untether` on its own. The idle limit, a denial and a new session still close it as before. |
| D32 | **Several Desktops on one backend share it** (found in use, 2026-11-10, with a Mac and a Windows PC on one host). Each Hermes Desktop is a client of the same host Hermes, so closing one Desktop also ends the chat open in the other. This comes from Hermes's one-backend design, not from the plugin, and the plugin cannot change it; documented under Limits. |
| D33 | **An Allow belongs to the caller that got it** (audit, 2026-11-20). The device hands a random grant token to the one call that obtained the person's Allow; every later call for that session must carry it, and closing needs it too. A caller without it (another program on the host speaking to the relay socket, a second Hermes process) makes the device ask again, with a text that says a different program is asking. Denials start a 60 s cool-down; prompts are rate-limited per host; session ids are validated. Link protocol major 2: host and devices update together. |
| D34 | **A lost connection is said, never replaced by the host** (audit, 2026-11-20; refined by D41 and D42). Connection state lives in one process's memory; when it is gone (a restart, another process, a changed session id, a time-out, a denial, a switch or a re-pair), the work meant for that device runs nowhere for the rest of that turn and the agent is told. Before every call the host re-checks that the session is still on that device, within its idle limit and with the key it was opened with; a switch to another device closes the first one; a file call chosen for a device never falls back to the host, even when the device's reply is malformed. |
| D35 | **Only the user's own turn reaches a device** (refines D23; extended by D56). Each tool call carries Hermes's turn id; a call from any other run (a background review, a scheduled job, a sub-agent, Hermes's own hook threads, which receive the turn id explicitly) works on the host. Runs no person typed open nothing and their words count as none: a platform or session source of cron, subagent, webhook, msgraph_webhook, kanban, tool, codex, gateway, a2a or bot_room (Hermes labels a `--source tool` integration and a managed worker by session source only, never by platform), a delegated child, a Hermes process started from a gateway or TUI agent's shell, and every turn Hermes injects itself (D56). Not detected: a Hermes started from a classic-CLI agent's shell, whose tool shells carry no session marks; it holds no grant token (D33), so the device asks its person before anything runs there. A call with no turn id falls back to the open-turn rule. |
| D36 | **The phrase starts a line the user typed** (refines D26/D31; mail, Slack threads and forwards in D57). `tether <device>` opens only when one line of the user's own words starts with it (never across a line break). Only the exact shapes Hermes builds are peeled (the turn's own sender tag, with the sender Hermes binds as the actor where a shared chat's route has no user, as in a Telegram observe-mode group; the email subject label; the Slack app-context label; Slack's thread context; a voice note's transcript); a quoted reply, mail quote or forward, a forward the gateway marks, attachment note, link preview, another agent's message or any other bracket line makes the words empty. |
| D37 | **A device's words are checked by shape** (audit, 2026-11-20; narrowed by D61). OS, shell and architecture from fixed lists, versions kept as their number only, paths only when absolute and plain. The model sees one narrow view (no rules paths, no name, no home in a listing); the pairing prompt shows the key first. |
| D38 | **Background jobs stay with their machine** (refined by D53). Hermes starts, polls and stops a background job by sending plain commands, later and from its own threads; a job's command is the job's own only when Hermes's registry sent it (its `spawn_via_env`, its poller, its `_signal_kill`, read from the call stack) and its whole text is what Hermes builds for that very job, found by Hermes's job id, never by pid. Those go to the machine the job started on, under the job's own session, whoever asks (the poller, the parent, a sub-agent's teardown, `/stop`) and whatever the route is now; the same text typed by the model is an ordinary command. Such calls are passive: they never prompt, never extend a session and never refresh its idle timer. |
| D39 | **Tether removes what it made, never the user's files** (the author, 2026-11-20). When a session closes, everything Tether created for it goes: the workspace, the files of its ended background jobs (a running job keeps running and its files go once it ends), the open-session record and Hermes's per-task file state for it (what its file tools read, their patch count, their file-state record; the terminal environment Hermes keys by 'default' on a device is shared with that machine's own runs and is not Tether's to end). Files the user made or asked for are never touched: no link is followed and a hard-linked file keeps its mode (D55). What is inside the workspace goes with it, including a file the agent moved there from elsewhere. The link socket is removed by its owner at a normal exit; after a hard stop (Hermes's gateway always ends with `os._exit`) it stays, harmless, until the next owner replaces it. (The link's temporary certificate copy is not a session's: it is written only when the stored `identity.crt` does not match the key's certificate, and deleted right after it is loaded.) |
| D40 | **The key passphrase is kept from accidental exposure; the machine's own user can still read it** (audit, 2026-11-21; corrects D13). The key file and its passphrase are files of that user (`.env` or the user's secret source; on macOS Hermes also puts every `.env` secret into the launchd job of a gateway it starts itself). Any program running as that user can read them: the agent's terminal on the host, and on a device during a session its person allowed. The system offers no same-user boundary a plugin can use without asking for a keychain (D13) or a second system user (D7), and a keychain item an interpreter may open also opens for a shell running that interpreter. So tether: removes the names from every process environment it loads in, first thing in `register()` and whatever the role, including the start-up copy (`ps -E`, `/proc/<pid>/environ`: the value bytes are overwritten in place, name and length kept); gives every terminal it makes an env that blanks them; removes them again at every tool call; masks the exact value under every spelling of the Hermes home; and has each device mask its own value in what it sends back. Not used: `prctl(PR_SET_DUMPABLE, 0)` (Hermes's own updater reads a running gateway's environment and would stop seeing how it is supervised; and it protects nothing while `.env` holds the value), and a command-pattern floor for reads of `.env` or the key file (bypassed by any indirection, so it would promise what it cannot keep). A stolen device key lets its holder stand in for that device toward the host, as a hostile paired device; a stolen host key still needs each device's Allow. The remedy is to unpair, make a new key and pair again. |
| D41 | **D34 is kept per session and judged by (session, turn)** (audit round 3, 2026-11-21; refines D34). Hermes's terminal environment key ('default' in the CLI, 'session:<chat key>' in the gateway) is shared by a parent, its delegate_task children, its `/bg` runs and the next conversation of the same chat, and its file tools carry another key (the session id), so neither key can carry D34. The host keeps, per session, the device its model was last told it works on, and, once the model is told inside a turn that the connection is gone, a hold for the rest of that turn that answers terminal and file work alike, a Hermes thread of that turn included. The decision is one step under the state lock, so of calls Hermes runs side by side one is told and the rest are held. A call is placed by its own turn id: a turn id that is no user turn of the session is another run, which works on the host and changes nothing; a call of the user's turn under a new session id (Hermes rotated it mid-turn) closes the old connection and is refused. A rotation Hermes reports at the turn's end closes the old connection and moves the unsaid note to the new id; one done between turns is matched by Hermes's conversation id on the next tool call. Hermes's own work after the turn (a MEDIA delivery) is refused while the model has not been told and spends nothing. Host-owned files are never held back. If Hermes cannot read the conversation's lineage it reports the session id itself, and a change between turns is then not recognised. |
| D42 | **The open-session record outlives its process** (audit round 3, 2026-11-21; refines D34). A clean exit loses the connection as a crash does, so the record is not removed at exit; only a close by the process that wrote it removes it. It carries a random per-process mark beside the pid (a later process can get the same pid), its holder re-dates it every 10 minutes while it holds the connection (the idle sweeper), it is never aged out while its process lives, and it is kept seven days after its holder last re-dated it. The next process that resumes the conversation says it once and removes it. |
| D43 | **A grant token goes only to the key that issued it** (audit round 3, 2026-11-21; refines D33). The host keeps, with each token, the key (fingerprint) of the link that handed it over. Every call that carries the token, and every close, is sent only over a link authenticated as that key, under whatever name the key has now: a rename keeps the key and the close reaches it under its new name. A name that now holds another key gets nothing: the session closes, and the old device ends its grant and empties its workspace at its own idle limit. The opening call of a connection carries no earlier token. `tether <device>` said again on the open connection first re-checks its key and idle limit; a changed key or a passed limit closes it and opens a new one, with a new Allow. |
| D44 | **Both sides count idle time the same way** (audit round 3, 2026-11-21). The device counts a session's idle time from the end of its last call, as the host does from the reply; a call still running is never idle on either side, so its grant, its workspace and its close stay put while it runs. The host closes slightly early (5 s, or a tenth of the limit if that is less), so it never sends a call into a grant the device has let lapse. `tether <device>` said again on the open connection is not a device call and moves neither clock. Background-job polls count on neither side (D38). |
| D45 | **A lost reply does not cost the Allow** (audit round 3, 2026-11-21). A new grant remembers the token its asking call presented. That same caller, whose reply with the new token was lost (the call failed or was stopped, or it was one of a parallel batch), rides the grant, is handed the current token and can close the session; an empty token never matches, so D33 holds. When a session's first call fails after the Allow, that grant ends at once. A token that reaches the host after the connection closed is sent back to the device, which ends that grant. |
| D46 | **The prompt names the session; one workspace per live session** (audit round 3, 2026-11-21). The prompt always shows the session id; a caller can no longer supply a title for it. A session id that would share a live session's workspace folder (a letter-case twin on macOS and Windows, or an id spelled like another id's folder name) is refused before anyone is asked, and `close_session` never empties a folder another live session works in. |
| D47 | **A consent prompt never outlasts the host's wait** (audit, 2026-11-21). Every call frame carries the host's deadline; the device shows its approval box for at most that long minus 3 s, and shows none when less than 20 s would be left (`consent.MIN_PROMPT_S`: a shorter box cannot be answered with a code; that call is refused and nothing counts as a Deny). The device announces its consent wait (`consent_wait_seconds`) and `devices use` waits that long plus 30 s, never less than 90 s. A config value outside 20–600 s is held to that range (`store.SETTINGS_LIMITS`; it was 5–600 s before the code box, D63). A prompt that ends unanswered for any reason (its own time-out, the host's Stop or time-out, a dropped link, Pause) kills its dialog, and the screen stays frozen until the dialog is gone. |
| D48 | **Pause is the kill switch** (audit, 2026-11-21). The flag the CLI and panel write is checked every second. On the change to paused the device ends every grant, drops the link, so every call in flight is stopped as for a lost connection (a running command is killed, one still waiting for its terminal never starts, a screen action waiting for the driver never reaches it, an open prompt closes), and ends every session at once. While paused the link comes back and every call is refused with the reason. Within that second the guard itself refuses an Allow or a result that arrives after the flag. |
| D49 | **Closing a session reaches work still waiting** (audit, 2026-11-21). A device call joins its session's stop handles when it is admitted, before its terminal is made and before it waits for the screen driver, so a close stops it there. Screen actions run one at a time on a thread of their own: an action waiting its turn holds no thread, and a driver call that never returns cannot starve terminal, file or close calls. |
| D50 | **A device session's terminal lives as long as its Allow** (audit, 2026-11-21; extends D39). Within a minute, the device's sweeper ends every session whose grant ended on the device without a close (its idle limit, Pause, a re-pair): its terminal with Hermes's shell snapshot, its stop handles, Hermes's file-tool state, its ended jobs' files and its workspace, as a close does. Pause and a re-pair do this at once. A session with a call in flight is kept until the call ends. Another session's use never ends a terminal whose Allow is live (the 30-minute eviction is gone). |
| D51 | **The host's label is checked by shape before it reaches the Allow prompt** (audit, 2026-11-21; the reverse of D37). The prompt names the host only when its label is one short line of plain characters (letters, digits, space and `. _ ' -`, at most 48); anything else shows as "the paired host". |
| D52 | **`execute_code` runs per call over tether** (audit, 2026-11-21). Hermes 0.23.3 prefers a persistent remote kernel on a non-local backend: a detached runner it later probes and stops by pid (`kill -0`, `pkill -P`, `rm -rf`) from session close, `/new`, idle reaping or another session's eviction, through whatever the route is then, and which outlives the session on the device. Every command from Hermes's remote-kernel code runs nowhere and fails, so Hermes falls back to its per-call path: each script is one foreground command on the routed machine, stopped with the turn and gone when it ends. Nothing persists between calls over tether. |
| D53 | **A background job's stop is real, and said** (audit, 2026-11-21). Hermes's stop text ends only its wrapper; on the machine the job runs on (a device, or this host), the plugin stops the job's whole process group and the wrapper's descendants (SIGTERM, then SIGKILL). A stop that did not happen (the device refused it, could not be reached, the connection is closed, the job is unknown) raises, so Hermes reports an error and keeps the job instead of marking it killed. A poll while the session is still connected to an unreachable device (D15) is "no news", for at most the idle limit. Job records live while Hermes tracks the job (at most 256); Hermes's environment teardown leaves jobs tracked (`cleanup_stops_processes = False`). Windows devices: no tree stop; the stop does nothing and says so. |
| D54 | **Hermes's own wrappers are not asked about again** (refines D25). Two internal commands are Hermes's fixed text around something already checked, so they carry the gate's note (the device's floors still apply): the background wrapper `spawn_via_env` builds around exactly the command the gate checked, and `execute_code`'s removal of the script folder it made for that call. Any other internal command is still judged by the device's full rules. |
| D55 | **Cleanup stays inside Tether's own sessions folder, whatever a session did to it** (audit round 3, 2026-11-21; refines D24/D39). On macOS and Linux the device holds its data folder open and reaches every name below it inside folders held open (`dir_fd`, `O_NOFOLLOW`), never by path: a link put in place of the sessions folder, a workspace, `skills` or anything deeper is removed itself, never followed, even if it appears while a cleanup runs; a folder of another file system mounted inside (a disk image, a share) is never entered. Only folders are chmod-ed; a lock flag or ACL (macOS) is cleared only on an entry with no other name, so a hard link (`ln`, a local `git clone`) never changes the person's own file. What cannot go (a file a program holds open, a lock Tether may not clear) is left, logged and retried by the sweeper; no cleanup raises. A data folder that is itself a link is refused: the device role does not start. Session ids with a control, format or line-separator character are refused. Windows has no folder-relative calls in Python: there each name is checked with lstat right before use (links, junctions and other reparse points are removed themselves), and a read-only mark is cleared only on a file with no other name. |
| D56 | **Hermes's own turns are not the user's** (audit round 3, 2026-11-21). A turn Hermes injects itself (another agent's Bot Mode message, a `/loop` wakeup, a `/goal` continuation or resume, a heartbeat, a background-job, sub-agent or kanban wake, a Bot Chat delivery, a plugin's injected message, a Desktop hidden widget send) or a message whose author is a bot works on the host and opens nothing, even while the user's device is open; its per-turn note says so, and the user's own next message reaches the device again. The plugin reads Hermes's own marks, never a guess: the display kind Hermes stamps on the turn's user row before `pre_llm_call` (a user's own message has none), the gateway turn's event (`internal`, `inherit_channel_pin`, a bot author), the first line of the prompts the classic CLI and the TUI queue as plain input (the `/loop`, `/goal` and heartbeat templates), and the Bot Mode signature. So `/goal` and `/loop` do not carry device work on by themselves, and they cannot keep a device's grant from going idle. A turn run in a separate managed-worker process carries none of these marks, but that process holds no connection or grant (D33, D34). |

## 3. Shape

One plugin package, two roles chosen by config. A machine can be a host, a device, or both.

```
        HOST (the agent's Hermes, e.g. NAS)                      DEVICE (e.g. the Mac's Hermes)
 ┌──────────────────────────────────────┐          ┌──────────────────────────────────────┐
 │ agent ─ tools                         │          │ tether device role                 │
 │   terminal/file tools ─▶ terminal     │          │   dials OUT to the host on boot      │
 │       provider "tether" ──┐         │  TLS 1.3 │   announces its capabilities         │
 │   computer_use ─▶ provider  ├─ link ◀─┼──────────┼─▶ runs each call through ITS OWN    │
 │       "tether" ───────────┤ listener│  mutual, │   Hermes: tool registry + approvals  │
 │   devices / device_call ────┘         │  pinned  │   ├ local terminal (its backend)     │
 │ Desktop tools: untouched (Hermes)     │          │   ├ computer_use (its cua-driver)    │
 └──────────────────────────────────────┘          │   └ its MCP servers / skill tools    │
                                                    └──────────────────────────────────────┘
```

### Host role registers (all public plugin API)
- **Terminal environment provider `tether`** (`ctx.register_terminal_environment_provider`):
  `execute(command)` → the session's active target. The four file tools (read_file, write_file, patch,
  search_files) are handed whole to the device by the `tool_execution` middleware instead (D22); anything else
  Hermes reads or writes through the environment rides on `execute()` (binary-safe transfer via base64 in the
  command is Hermes's job).
  `is_remote = True`; no `exec_prefix` (Bot Desktop never placed on a device). **`local` is always a
  target**, so the host keeps its own machine (committee: provider must not swallow host-local work).
- **Computer-use provider `tether_screen`** (`ctx.register_computer_use_provider`, in its own plugin; see Packaging below): the 11 `ComputerUseBackend`
  methods (capture, click, drag, scroll, type_text, key, list_apps, list_windows, focus_app, set_value, wait)
  forwarded as calls; results carry screenshots as binary blobs.
- **Tools** (`ctx.register_tool`, toolset `tether`):
  - `devices` — list paired devices, online/asleep since, capabilities, active device; `use <device>`.
  - **Device MCP/skill tools** (planned, not built in 0.2) — registered per device **with their real schemas** as they are announced
    (`mac__bambu_status`, …; `check_fn` hides them while the device is asleep), so the model sees proper
    descriptions and arguments (committee: a generic `device_call(name, args)` makes models fumble).
    Device side reads its tool list from its own Hermes MCP configuration; if Hermes exposes no stable API
    for that, the device plugin starts its enabled MCP servers itself from its config. (Stretch: day 4.)
- **Link listener** — an asyncio server on its own event-loop thread, bound to a configured address
  (tailnet IP in our setup). Tool handlers (sync, in Hermes's worker threads) hand calls to it with
  `run_coroutine_threadsafe` and wait on a future with the call's deadline; it never touches Hermes's own
  loops. **One process owns it, every host process uses it** (found live 2026-11-06: Desktop sessions run
  in the dashboard backend, not `gateway run`; the SSH Desktop route starts its own `serve` child). The
  first process to take `tether/link.lock` owns the device listener and serves a private relay on
  `tether/link.sock` (0600 in the 0700 data folder); every other process relays through it. The gateway
  claims ownership at boot so devices connect before any call; if the owner exits, the next process that
  needs the link takes over and devices reconnect on their own (`hostlink.py`, tests/test_hostlink.py). An owner
  that cannot listen yet (address not up at boot, port taken, a pin it cannot load) keeps the link and its relay
  and retries every few seconds; if the service cannot be built or started, the lock is released (D62).

### Packaging: two plugins in one repo (found 2026-11-06)
Hermes loads computer-use providers from their **own plugin folders** through a limited collector
(`plugins/computer_use/__init__.py`), and classifies any plugin whose source mentions the computer-use
contract as kind `exclusive`, outside the general plugin manager (`hermes_cli/plugins_manifest.py`).
So the repo ships **`tether`** (general: link, pairing, device role, terminal provider, `devices`
tool; its source never mentions the computer-use contract) and **`tether_screen`** (computer-use
provider; `computer_use.backend: tether_screen`), which reaches `tether`'s link in the same process
through a small process-wide runtime handle. Two catalog entries, one repo (`subdir:` per entry).

### Device role
- **Desktop machines only** (D12): a device is a machine someone sits at (Mac first). Headless servers
  stay on SSH; tether changes nothing there.
- Dials out to the host on start and keeps the link (backoff reconnect). Nothing listens on the device.
- Reachable only while the device's Hermes runs (Desktop or its gateway service); otherwise the host
  shows `offline: Hermes not running` (D18).
- **Announce**: device name, OS, OS version, architecture, Hermes version, the shell its Hermes uses, terminal,
  computer_use available, home path, and whose rules apply (its Hermes home, write-safe root, session workspace
  root, idle limit). The host keeps only what passes its checks (D37, D61).
- **Execute** every call through the device's own Hermes:
  - terminal → the device's configured local terminal environment, through the dangerous-command gate;
  - file tools → `model_tools.handle_function_call` (the device's hooks, middleware and file rules; D59);
  - computer_use → the device's own computer-use backend in `standard` mode (its driver, its TCC grants);
  - MCP/skill tools → the device's MCP client registry, only servers enabled on the device (planned, not built
    in 0.2).
- **Presence-based session grant (D10, the author 2026-11-06).** No auto mode, ever. Control of a device must be
  allowed **by a person sitting at that device**:
  1. The first tether call of a host session (any capability) puts a **consent prompt on the device's
     own screen**: "Hermes on <host> wants to use this Mac (screen, terminal, files, tools) for session
     *<session id>*. Allow for this session / Deny" (D46: always the id, never caller text). Shown as a native
     dialog: macOS `osascript`, Windows a message box through PowerShell; there is no Linux prompt yet, so a Linux
     device refuses every session. No answer = deny.
  2. **One approval covers that session**: no per-action prompts after it.
  3. The grant is keyed (host, host session id). A **new session needs a new approval**.
  4. **Idle timeout**: a session that makes no tether call for `grant_idle_minutes` (device setting,
     default 15, user-chosen; §6; counted from the end of its last call, and a call still running is never idle, D44)
     **loses the grant**; the next call prompts on the device again.
  5. The device can end every grant at once (Pause, the kill switch): within a second it drops the link,
     which stops every call in flight the way a lost connection does, and ends every session (D48); host
     session end also ends it.
  6. Hermes's built-in hard blocks still apply inside a granted session (no empty trash / force delete /
     lock / log out key combos; no `curl | bash`, `sudo rm -rf /`; no clicking permission dialogs or
     typing passwords).
  7. **The agent can never click its own consent** (found in the day-1 spike): while a consent prompt is
     open, the device **freezes all computer-use input from every session** until a human answers; no
     grant means no screen control, so the first prompt of a session is safe by construction.
  Spike result 2026-11-06: native macOS dialog works (answer back in 4 s, default Deny, timeout = deny);
  it appears on the logged-in user's physical screen even when raised from an SSH shell, so answering
  always takes a person at that screen.
  Consequences, all intended: nothing can start while nobody is at the device; a locked or sleeping
  device cannot be taken; approvals are never sent to a phone or another machine (they come from the
  device's own screen).
  Spike day 1: show the prompt on the Mac from a tether call (Desktop card or `osascript`) and get the
  answer back; confirm it cannot be answered remotely.

### Why this beats tonight's spike
The spike forwarded at the *driver* level and hit three traps (driver manifest names a local path; Bot
Desktop placement; a private daemon launched via a local `open -a`). Executing on the device inside the
device's own Hermes avoids all three: the driver, daemon and permissions are local where they belong.

## 4. Link protocol

- **Transport**: one TCP connection per device, device → host, TLS 1.3 (below). Keepalive ping 20 s.
- **Framing**: 4-byte length + JSON header, optional binary body (screenshots, file chunks).
- **`hello`** carries `protocol: {major, minor}` (a device's also its name and plain facts, D61); same major
  required (D17).
- **Reconnect** keeps session grants that are still inside their idle window (D15).
- **Background processes** (Hermes's start/poll/stop of a background job) ride the ordinary `exec` call, marked
  passive, implemented only through the public plugin API (D16, D38, D53).
  `hello` · `call{id, kind, args, deadline, chunked}` · `result{id, ok, data, error, chunked}` ·
  `chunk{id, seq, last}` · `cancel{id}` · `event{kind, data}` (the device's `announce`) · `ping/pong`.
- **Calls** are request/response with per-call deadlines and cancel; the host never blocks the agent
  past the deadline. Device offline → immediate `<name> is offline since HH:MM (asleep, or its Hermes is not
  running)` (queueing is v2).
- **Multiplexed**: many calls in flight on one link; every frame carries its call id. Bodies larger than
  256 KB go as `chunk{id, seq, last}` frames **interleaved** with other traffic, so a big file never stalls
  a screenshot or a command. Hard cap per call (e.g. 64 MB) with a clear error above it.
- **Sizes**: screenshots ~250 KB–1.5 MB measured (PNG; JPEG option for previews).
- **Announce is live**: the device re-announces when its panel settings change (idle limit, consent wait), not
  only on connect.

## 5. Security

### 5.1 Identity
- Host and each device own a long-term key pair (Ed25519) and a self-signed certificate made from it,
  generated with `cryptography` (already a Hermes dependency).
- **Storage (D13)**: each private key is stored ENCRYPTED in the plugin's data folder; the passphrase that
  unlocks it is a named Hermes secret, `TETHER_KEY_PASSPHRASE` (legacy `HOMEPORT_KEY_PASSPHRASE`), kept the way
  Hermes keeps every secret (`.env` by default, or the user's configured secret source). The plugin never calls
  a keychain itself. Only the link code loads the key, in-process, at connect time. Certificates and pins are not
  secret.
- **Keeping the passphrase out of sight (corrected 2026-11-21, D40)**: Hermes loads `.env` into the process
  environment; gives a gateway it starts itself every `.env` secret in its start-up environment; lays a
  multiplexed profile's secret scope (that profile's `.env`) over the environment of every foreground terminal
  child; and can load `.env` into the environment again at any time (a cron job's start, a reload). A terminal
  provider's `strip_env_keys` is not applied to foreground terminal children. So the plugin:
  - in every Hermes process it loads in, first thing in `register()` and whatever the role: reads the passphrase
    once and keeps it in memory per Hermes home (keyed by the resolved home); removes both names from
    `os.environ`; overwrites their values in the process's start-up environment (macOS: the strings
    `KERN_PROCARGS2` reads, found through `_NSGetArgv`, read back with `vm_read_overwrite` before anything is
    written; Linux: `/proc/self/environ`'s area through `/proc/self/mem`; the name and length stay, the value
    becomes `*`); and registers the exact value with Hermes's masking (`register_vault_redaction_value`) under the
    home as named then and as the process names it (they differ when the home is reached through a symlink);
  - gives every terminal it creates (the host's local target, each device session) `env={name: None}`: Hermes
    lays a terminal's own env over everything else and drops a `None`, so no child of those terminals has the
    names, whatever `os.environ` or a profile scope holds at that moment;
  - removes the names from `os.environ` again at the start of every tool call (`tool_execution` middleware) and
    before a device runs a host's file tool, and refreshes the mask under that call's home;
  - lists them in `strip_env_keys`, which Hermes applies to the children its own sanitizers build (background
    and PTY terminal children, `execute_code`, helper processes);
  - declares them with `register_session_env`, which keeps them out of Hermes's shell snapshots. Its `None`
    value does not unset them in a child on Hermes 0.23.3: Hermes drops a session-env value for a name any
    terminal provider lists in `strip_env_keys`, and those lists stay for the background children;
  - on a device, replaces its own passphrase with Hermes's mask mark in the output of every command and file
    tool before it leaves the machine, since the host never holds that value.
  Not covered: a command that reads the files (D40); and on a gateway serving several profiles, Hermes's own
  local terminal (not tether's) gives its foreground children that profile's `.env` names, the passphrase
  included, masked in output. Asks for Hermes: apply `strip_env_keys` (or a `None` session-env value) to
  foreground terminal children; refuse or flag terminal reads of `$HERMES_HOME/.env` as `read_file` already does.
  Earlier versions of this section promised the stripping and the redaction; 0.1 did neither.

### 5.2 Every boot: automatic handshake (D5)
- **TLS 1.3 only**, **mutual** authentication, both certificates **pinned by SHA-256 fingerprint**
  (no CA, no hostname trust). Ephemeral X25519 key exchange → forward secrecy.
- **256-bit enforced**: immediately after the handshake, **before any application byte is read or
  written**, each side checks the negotiated suite and **closes the link unless it is
  `TLS_AES_256_GCM_SHA384` or `TLS_CHACHA20_POLY1305_SHA256`**. Both Hermes Pythons (Mac 3.11/OpenSSL 3.5.6,
  NAS/OpenSSL 3.5.9) already list AES-256-GCM first; the check turns that default into a guarantee.
  Python's stdlib cannot pre-restrict TLS 1.3 suites (`set_ciphers` rejects TLS 1.3 names and leaves the
  1.3 list untouched; no `set_ciphersuites`), so the check-before-data gate is the enforcement point
  (verified 2026-11-06). `minimum_version = TLSv1_3`.
- **Suite choice is automatic and non-invasive (D11)**: both 256-bit suites are allowed and TLS negotiates
  the best one for the device ↔ host pair on every connect; nothing on the user's system is configured or
  changed (no process-wide OpenSSL config). Both suites are equally strong; AES-256-GCM wins wherever AES
  hardware exists (measured on the Mac: AES-256-GCM 8,858 MB/s vs ChaCha20-Poly1305 2,303 MB/s), and
  ChaCha20 stays available for chips without it. `devices` and the Tether panel show the negotiated suite and its
  bits (read-only).
- **Proven live 2026-11-06**: mutual TLS 1.3 NAS (OpenSSL 3.5.9) ↔ Mac (3.5.6) with pinned certs
  negotiated `TLS_AES_256_GCM_SHA384` on both ends; gate PASS; data flowed.
- Python stdlib `ssl` + `cryptography`; no homemade cipher or handshake.

### 5.3 Pairing: the master link (D5)
1. On the host: `hermes tether pair mac` → a one-time **pairing link**
   `tether://<host>:<port>/#<host_fp>.<secret>`: the **host's certificate fingerprint** plus a 128-bit
   random secret, single use, 10-minute expiry, bound to the device name (the device's own `name:` setting must be
   the same; letter case is free, and `local`, `host` and `all` are reserved); shown as text, which the owner
   carries to the device.
2. On the device: `hermes tether join` reads the link from **stdin or a hidden prompt** (an argument still
   works but prints a warning: it is visible to other programs and kept in shell history) (no shell
   history, no `ps`).
3. The device opens TLS 1.3 to the host and **aborts unless the host certificate's fingerprint equals
   `host_fp` from the link** (a fake host at that address fails here, before anything else). The 256-bit
   gate (§5.2) runs next. The host sends a fresh 16-byte `nonce`. Each side then proves knowledge of the
   secret **without sending it**:
   - device → `HMAC-SHA256(secret, "device" ‖ host_fp ‖ device_fp ‖ name ‖ nonce)`
   - host → `HMAC-SHA256(secret, "host" ‖ host_fp ‖ device_fp ‖ name ‖ nonce)`
   Fingerprints are exchanged in the clear inside TLS so each side can recompute; a man-in-the-middle sees
   different fingerprints on each side, so neither HMAC verifies; the nonce defeats replay.
4. **The host asks its owner to confirm** the new device on the host's own terminal before pinning: "Device
   'mac' wants to pair: key 4f2a…" first, then the checked facts ("os Darwin, Hermes 0.23.3"), then "Pair it?
   [y/N]". A thief who races the real device with a stolen link still needs
   that yes.
5. Both pin the other's fingerprint; the secret is burned atomically (used or expired = gone). The host sends
   its answer first and pins the device only once it went out: a device that left while the owner read the prompt
   is not pinned, and `pair` says so at once (D62). From then on, §5.2 every boot.
- A 128-bit secret needs no PAKE (PAKE protects low-entropy codes). Three wrong proofs revoke the link anyway;
  failures are logged.

### 5.4 Revocation and control
- Host: `hermes tether unpair mac` removes the pin; the host cuts the device's live link within a few seconds
  (its pin watcher) and refuses every later connect.
- Device: `hermes tether unpair` removes the host pin; a device-side **pause** refuses every call and, within a
  second, stops the calls already in flight and ends every session (D48).
- Screen control is Hermes's built-in computer use as is (D14): its background-first input and its own
  cursor overlay show what the agent does; tether adds no takeover or arbitration logic.

### 5.5 Threat model (summary)
| Threat | Answer |
|---|---|
| Stolen pairing link | Single use, 10 min, bound to a name; after use it is worthless. |
| MITM during pairing or later | Pairing HMAC binds both fingerprints; later connects require both pins. |
| Another program on the host (same OS user) | It cannot ride an allowed session: the Allow belongs to the caller that got it (D33), and the token goes only to the key that issued it, on every close path, even after it re-pins or renames devices in the pins file (D43). A twin of a session id can neither open nor empty a live session's workspace (D46). It can start its own Hermes; the device then asks its person again. It can delay opens (a Deny locks that session id for a minute; its prompts count against the host's budget), which gains it nothing it could not get by unpairing the device. |
| A paired device turned hostile | Its announced facts are checked by shape and the model sees a short list (D37); its home is used only in home-folder shape (D60); its replies cannot make a file call fall back to the host (D34). It still controls the output of the commands it runs. |
| Stolen device key (e.g. a prompt-injected agent reading it via the terminal) | Not prevented (D40): the key file and its passphrase are readable by any program of the device's user, the agent's terminal in an allowed session included; masking catches only the plain value. The holder can stand in for that device toward the host (as a hostile paired device) until it is unpaired and makes a new key; it cannot reach the device itself. |
| Mismatched plugin versions | `hello` protocol version check; clear refusal (D17). |
| Weaker crypto negotiated | Link closes unless a 256-bit suite was negotiated. |
| Prompt injection on the host | Control needs a fresh code from the person's authenticator app, typed into the device's own box, per session (D10, D63); the link carries no code; idle grants expire; hard blocks stay on. Only a line the user typed opens a device (D36, D57); another agent's message and Hermes's own follow-up turns neither open one nor use an open one (D56). |
| Text the user did not type that still counts | Forwards Hermes passes on unmarked, a mail whose first line is someone else's text, and a Hermes started from a classic-CLI agent's shell (D35, D57): the device's code box is the gate (D63). |
| Something on the device clicking or typing (an accessibility app, the agent's own screen actions, someone at the machine without the phone) | Clicking approves nothing; typing needs the current code. Every screen action is refused while the box is open (D65). Guesses: 3 per request, a pause after every 5 in a row, a lock after 20 (P <= 6 x 10^-5 before the owner's unlock) (D68). |
| Replay of a code someone saw | Each 30-second code is accepted once, recorded on disk (sealed) before the grant, and the running Hermes refuses codes from before its start (D68). |
| The agent or another program reads the authenticator's seed | A sealed 0600 file in Tether's data folder (macOS: under Tether's key passphrase; Windows: DPAPI). On macOS during a session the lock keeps the agent's commands and file tools (which run inside it, D79) from it and from `.env` (D70, D79). Outside a session, and on Windows (commands unlocked by default), a program running as the person can read it (stated, D66). The seed is never in plain form in a file, log, frame, argument, environment or the host, and is masked in device output. A program that changes Tether itself is not stopped. |
| Someone sets up, replaces or removes the authenticator | Only at the device, in boxes: turning it on needs no other proof (no session can exist before it), replacing or removing it the current code or a recovery code; on macOS a session cannot write the data folder; nothing on the link, argv, stdin or a file (D67). |
| Host compromised | Host is the trusted root by design; the device's approvals, rules and pause limit the blast radius. |
| Exposed port | Devices listen on nothing; the host binds one configured address. |
| A session's commands aim the device's cleanup at the person's files (a link in place of the sessions folder or inside it, a hard link, a mounted volume, a locked or ACL-protected entry) | Cleanup works inside folders held open and never follows a link, never enters another file system, never changes a hard-linked file's mode, flags or ACL, and never raises (D55). What the agent itself moves into its workspace goes with it. |
| Secret leakage via env | The key passphrase leaves every environment of the processes the plugin loads in, the start-up copy included, never reaches a child of a terminal the plugin makes, and is masked in output, by each device for its own value too (5.1). Hermes's own provider-key filtering and redaction stay on. |

```yaml
# host (e.g. a home server)
terminal:
  backend: tether          # agent terminal/files go to the active device
computer_use:
  backend: tether_screen
plugins:
  entries:
    tether:
      settings:
        role: host
        listen: 192.0.2.10:9130

  entries:
    tether:
      settings:
        role: device
```

**`grant_idle_minutes`** (device setting, default **60**, D77): the user picks their own value in the Tether panel on

**device**, so each machine's owner decides how long their own machine stays granted; the host can only set a
shorter limit of its own (D29). A new value applies to the
next idle check (existing grants are measured against it immediately).

## 7. Known traps (from the spike and the live tests) and how v1 handles them
Three kinds of fix: **tether** (in this plugin), **Hermes** (a Hermes core change, proposed upstream, never
installed by tether; patches and evidence in `docs/hermes-patches/`), **driver** (cua-driver, upstream).

| Trap | Handling |
|---|---|
| Driver `manifest` names an absolute local path | N/A: the driver runs on the device inside its own Hermes. |
| `bot_desktop.placement: auto` builds a Linux Xvnc on the remote | Host never uses Bot Desktop for devices (provider has no `exec_prefix`). |
| Private daemon launched via local `open -a` (bounded/unrestricted) | Device launches it locally. |
| **Fullscreen apps / other Spaces cannot be focused** (live 2026-11-06: `focus_app Claude` → "No on-screen window found" while Claude was fullscreen) | **Hermes.** Its cua backend lists windows with `on_screen_only: true` (`tools/computer_use/cua_backend_capture.py:175`) and `focus_app` matches only that list, so any window on another Space (every fullscreen app) is invisible; the driver itself lists all Spaces and `bring_to_front` switches to them. Known upstream: issue NousResearch/hermes-agent#142478 (open) and PR NousResearch/hermes-agent#29031 (open, all-Spaces listing for captures). Our proposal `docs/hermes-patches/focus-app-other-spaces.patch` looks across Spaces only for `raise_window=true`, explains the no-raise case (`window_on_other_space`), and was verified live both ways (Space 435 ↔ 1). Same behaviour locally; tether inherits the fix with no plugin change. Until it lands: the person at the Mac leaves fullscreen, or the agent reports the step as skipped. |
| Fullscreen raise reported "unverified" | **Driver** (part) + Hermes patch. In fullscreen the app's own 32 px title strip is a separate window above the content window; cua-driver 0.28.2 then reports `bring_to_front_exact_window_unverified` although the window is focused and its app frontmost. cua-driver **0.30.4** (PR trycua/cua#3785) changed the check to "frontmost process, focused, front within its process on its display"; tested 2026-11-06 after updating the Mac to **0.38.0**: still unverified, now with `front_in_process_on_display=false` (the strip is the front window of the app's own process). So the Hermes patch keeps accepting exactly that observed state (focused window == target, frontmost pid == target pid), and the strip case is worth a cua-driver issue. Patch v2 also makes the accepted result fully consistent (`verified`, `effect`, `status`), and captures of a fullscreen app target its titled content window instead of the 24 px strip. Applied locally on the Mac (device) only; undo in `docs/hermes-patches/README.md`. |
